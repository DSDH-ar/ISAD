# 面向服务架构（SOA）系统设计 —— 古籍文献数字化平台

## 问题 1：面向服务设计

### 1.1 服务边界划分与核心服务清单

按照「基础能力服务 → 业务服务 → 编排服务」三层划分，能力层只提供原子可复用能力，业务层面向具体业务场景，编排层负责跨服务流程串联，三层之间单向依赖、禁止跨层直连底层存储。

#### 一、基础能力服务（原子能力，可独立复用）

| 服务名称 | 职责 | 复用方 |
|---|---|---|
| OCR 识别服务（ocr-service） | 接收影像文件引用，调用可插拔 OCR 引擎输出结构化文本与置信度 | 文本校对、实体标注、批量数字化、上层系统 |
| 实体标注服务（annotation-service） | 对 OCR 文本进行人物/地名等实体识别与人工标注，输出标注记录 | 研究人员校对流程、专题汇编、检索索引 |
| 元数据著录服务（metadata-service） | 古籍元数据（题名、版本、朝代、著者、密级等）的增删改查与校验 | 各业务服务、上层系统 |
| 文件存储服务（storage-service） | 影像大图的存取、分片上传、缩略图生成、存储引用管理 | OCR、著录、检索、门户展示 |
| 权限管控服务（auth-service） | 用户认证、三级密级（开放/校内/涉密）鉴权、访问控制列表 | 所有对外接口的前置鉴权 |
| 审计日志服务（audit-service） | 统一记录操作留痕：操作人、时间、对象、变更内容 | 所有写操作服务 |
| 全文检索服务（search-service） | 基于 OCR 文本与元数据构建索引，提供检索 | 检索业务、门户、成果系统 |

#### 二、业务服务（面向业务场景）

| 服务名称 | 职责 |
|---|---|
| 数字化加工服务（digitization-service） | 影像上传 → 著录 → OCR → 校对的业务受理与状态管理 |
| 文献管理服务（collection-service） | 古籍档案的审核、密级定级、开放/冻结管理 |
| 专题汇编服务（compilation-service） | 按专题聚合标注数据，导出专题数据集 |
| 访客浏览服务（visitor-service） | 匿名用户公开浏览与简单检索，内部强制走 auth-service 密级过滤 |
| 开放接口服务（openapi-service） | 面向图书馆门户、学术成果系统的对外数据 API 网关 |

#### 三、编排服务（跨服务流程调度）

| 服务名称 | 职责 |
|---|---|
| 数字化流水线编排服务（pipeline-orchestrator） | 编排"上传→著录→OCR→实体标注→人工审核→发布"全流程，基于事件驱动推进 |
| 成果发布编排服务（publish-orchestrator） | 编排审核通过后的发布动作：更新密级→刷新索引→通知门户/成果系统 |

```json
// 接口：POST /api/v1/annotations —— 提交一条实体标注
// 请求
{
  "ocr_text_id": "OCRTEXT202611200001",   // 必填，关联的 OCR 文本记录

  "char_end": 15,                         // 必填，结束偏移（左闭右开）
  "source": "MANUAL",                     // 必填，枚举：MANUAL / MACHINE（机器预标+人工确认）

// 成功响应 201
{
  "code": 0,
  "data": {
    "annotation_id": "ANNO2026112000031",
    "status": "SUBMITTED",               // SUBMITTED → REVIEWED → PUBLISHED
    "created_at": "2026-11-20T17:35:10+08:00"
  }
}

// 异常返回
{ "code": 40010, "message": "ocr_text_id 不存在" }                          // HTTP 400
{ "code": 40011, "message": "char_start/char_end 超出文本范围" }            // HTTP 400
{ "code": 40012, "message": "entity_type 取值非法" }                        // HTTP 400
{ "code": 40301, "message": "该古籍为涉密管控，当前用户无标注权限" }          // HTTP 403

{ "code": 50002, "message": "标注持久化失败，请重试" }                       // HTTP 500
```

### 1.3 服务解耦方式与同步/异步场景选择

**解耦手段：**

1. **契约先行**：服务间只依赖接口契约（REST/JSON Schema），不依赖对方内部实现与数据库表结构；
2. **引用传递而非实体传递**：服务间传 `image_ref`、`book_id` 等引用 ID，影像等大对象由 storage-service 统一托管，避免数据拷贝与耦合；
3. **事件驱动**：写操作完成后发布领域事件（如 `OcrCompleted`、`AnnotationReviewed`），订阅方自行响应，生产者不感知消费者；
4. **可替换点适配**：OCR 引擎通过适配器接口接入（引擎 A/B 可配置切换）；数据访问统一走各服务内部仓储层，更换数据库只影响单服务内部；
5. **审计与鉴权横切**：日志、权限通过统一拦截/网关接入，业务服务不重复实现。

**同步调用 vs 消息队列异步调用：**

| 场景 | 方式 | 理由 |
|---|---|---|
| 鉴权校验、查询单条元数据、检索接口 | **同步** | 调用方必须立刻拿到结果才能继续（如不通过鉴权需直接拒绝请求），且耗时短（毫秒级），同步最简单可靠 |
| OCR 识别任务、批量数字化流水线 | **异步（消息队列）** | 单页大图识别耗时数十秒，同步会长时间占用连接并超时；用队列削峰，失败可重试，编排服务通过事件推进下一环节 |
| 发布后刷新检索索引、通知门户/成果系统 | **异步（消息队列）** | 发布方不关心下游何时完成，下游短暂不可用不应阻塞发布主流程；队列天然支持多订阅方（索引、通知各自消费） |
| 审计日志写入 | **异步** | 日志不应拖慢主业务，也绝不因日志失败导致业务失败（最终一致即可） |

选择原则：**需要立即拿结果决策的短操作用同步；耗时长、可延迟、需要削峰重试或多下游传播的用消息队列异步**。

## 问题 2：数据层概念与逻辑模型设计

### 2.1 E-R 图（实体-属性-关系清单）

**核心实体与属性（★ 主键，FK 外键）：**

1. **用户 User**：<u>user_id</u>★、username、password_hash、role（ADMIN/RESEARCHER/ARCHIVIST/ANONYMOUS）、status
2. **古籍 Book**：<u>book_id</u>★、title、author、dynasty、version（版本）、source_place（来源地方）、resource_type（古籍/地方志/族谱，可扩展）、access_level（OPEN/CAMPUS/RESTRICTED 三级密级）、status（著录中/已审核/已发布）、created_by FK→User、created_at
3. **影像文件 ImageFile**：<u>image_id</u>★、book_id FK→Book、page_no、file_ref（对象存储引用）、format（TIFF/JPG）、resolution、file_size、thumbnail_ref
4. **OCR 文本 OcrText**：<u>ocr_text_id</u>★、image_id FK→ImageFile、book_id FK→Book（冗余查询列）、page_no、text_content、engine（OCR 引擎标识）、confidence、proofread_status（未校对/已校对）、proofreader_id FK→User
5. **标注记录 Annotation**：<u>annotation_id</u>★、ocr_text_id FK→OcrText、book_id FK→Book、entity_type（PERSON/PLACE/OTHER）、entity_name、char_start、char_end、source（MANUAL/MACHINE）、review_status（SUBMITTED/REVIEWED/PUBLISHED）、annotator_id FK→User、reviewer_id FK→User
6. **用户权限 UserPermission**：<u>perm_id</u>★、user_id FK→User、access_level（可访问的密级范围）、resource_scope（可操作资源类型）、granted_by FK→User、granted_at
7. **操作日志 OperationLog**：<u>log_id</u>★、user_id FK→User、book_id FK→Book、action（CREATE/UPDATE/REVIEW/PUBLISH/DOWNLOAD…）、target_table、target_id、detail（变更前后摘要 JSON）、operated_at、ip

**关系（基数）：**

| 关系 | 基数 | 说明 |
|---|---|---|
| User — Book | 1 : N | 一个管理员著录多部古籍（created_by） |
| Book — ImageFile | 1 : N | 一部古籍多页影像，每页一条影像记录 |
| ImageFile — OcrText | 1 : 1..N | 一页影像至少一条 OCR 文本（可多次识别保留版本） |
| Book — OcrText | 1 : N | 逻辑上属于古籍（冗余外键便于按书检索） |
| OcrText — Annotation | 1 : N | 一段 OCR 文本上可有多个实体标注 |
| User — Annotation | 1 : N（标注人）、1 : N（审核人） | 双角色关联 |
| User — UserPermission | 1 : N | 一个用户可有多条权限授权记录 |
| User — OperationLog | 1 : N | 一个用户产生多条操作日志 |
| Book — OperationLog | 1 : N | 一部古籍被多次操作留痕 |

### 2.2 核心数据表设计（MySQL 风格）

```sql
-- 1. 古籍主表
CREATE TABLE book (
  book_id        VARCHAR(32)  NOT NULL COMMENT '业务编号',
  title          VARCHAR(200) NOT NULL COMMENT '题名',
  author         VARCHAR(100)          COMMENT '著者',
  dynasty        VARCHAR(50)           COMMENT '朝代',
  version        VARCHAR(100)          COMMENT '版本',
  source_place   VARCHAR(100)          COMMENT '来源地方',
  resource_type  VARCHAR(20)  NOT NULL DEFAULT 'GUJI' COMMENT '资源类型:GUJI/DIFANGZHI/ZUPU',
  access_level   TINYINT      NOT NULL DEFAULT 0 COMMENT '密级:0开放/1校内/2涉密',
  status         TINYINT      NOT NULL DEFAULT 0 COMMENT '状态:0著录中/1已审核/2已发布',
  created_by     VARCHAR(32)  NOT NULL,
  created_at     DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (book_id),
  KEY idx_title (title),                                  -- 题名检索
  KEY idx_type_level_status (resource_type, access_level, status), -- 访客按密级+类型过滤
  KEY idx_created_by (created_by)
);

-- 2. 影像文件表
CREATE TABLE image_file (
  image_id     VARCHAR(32) NOT NULL,
  book_id      VARCHAR(32) NOT NULL,
  page_no      INT         NOT NULL COMMENT '页码',
  file_ref     VARCHAR(500) NOT NULL COMMENT '对象存储引用(非文件本体)',
  format       VARCHAR(10) NOT NULL DEFAULT 'TIFF',
  resolution   VARCHAR(20)          COMMENT '分辨率如 600dpi',
  file_size    BIGINT               COMMENT '字节数',
  thumbnail_ref VARCHAR(500)        COMMENT '缩略图引用',
  uploaded_by  VARCHAR(32) NOT NULL,
  created_at   DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (image_id),
  UNIQUE KEY uk_book_page (book_id, page_no),   -- 同书同页唯一
  KEY idx_book (book_id)
);

-- 3. OCR 文本表
CREATE TABLE ocr_text (
  ocr_text_id      VARCHAR(32) NOT NULL,
  image_id         VARCHAR(32) NOT NULL,
  book_id          VARCHAR(32) NOT NULL COMMENT '冗余查询列',
  page_no          INT         NOT NULL,
  text_content     MEDIUMTEXT  NOT NULL COMMENT 'OCR 全文',
  engine           VARCHAR(50) NOT NULL COMMENT 'OCR 引擎标识,支持替换',
  confidence       DECIMAL(4,3)         COMMENT '平均置信度',
  proofread_status TINYINT     NOT NULL DEFAULT 0 COMMENT '0未校对/1已校对',
  proofreader_id   VARCHAR(32),
  created_at       DATETIME    NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (ocr_text_id),
  KEY idx_image (image_id),
  KEY idx_book_page (book_id, page_no),           -- 按书翻页读取
  KEY idx_proof (proofread_status)                -- 待校对任务队列
);

-- 4. 标注记录表
CREATE TABLE annotation (
  annotation_id VARCHAR(32) NOT NULL,
  ocr_text_id   VARCHAR(32) NOT NULL,
  book_id       VARCHAR(32) NOT NULL,
  entity_type   VARCHAR(10) NOT NULL COMMENT 'PERSON/PLACE/OTHER',
  entity_name   VARCHAR(100) NOT NULL,
  char_start    INT NOT NULL,
  char_end      INT NOT NULL,
  source        VARCHAR(10) NOT NULL DEFAULT 'MANUAL' COMMENT 'MANUAL/MACHINE',
  review_status TINYINT NOT NULL DEFAULT 0 COMMENT '0待审/1已审/2已发布',
  annotator_id  VARCHAR(32) NOT NULL,
  reviewer_id   VARCHAR(32),
  created_at    DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (annotation_id),
  KEY idx_text_pos (ocr_text_id, char_start),     -- 定位文本位置
  KEY idx_entity (entity_type, entity_name),      -- 按实体聚合(专题汇编)
  KEY idx_book_status (book_id, review_status)    -- 按书审标注
);

-- 5. 用户权限表
CREATE TABLE user_permission (
  perm_id        VARCHAR(32) NOT NULL,
  user_id        VARCHAR(32) NOT NULL,
  access_level   TINYINT NOT NULL COMMENT '可访问最高密级:0/1/2',
  resource_scope VARCHAR(20) NOT NULL DEFAULT 'ALL' COMMENT '可操作资源类型范围',
  granted_by     VARCHAR(32) NOT NULL,
  granted_at     DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  PRIMARY KEY (perm_id),
  UNIQUE KEY uk_user_level_scope (user_id, access_level, resource_scope),
  KEY idx_user (user_id)
);

-- 6. 操作日志表
CREATE TABLE operation_log (
  log_id      BIGINT       NOT NULL AUTO_INCREMENT,
  user_id     VARCHAR(32)  NOT NULL,
  book_id     VARCHAR(32)  NOT NULL,
  action      VARCHAR(20)  NOT NULL COMMENT 'CREATE/UPDATE/REVIEW/PUBLISH/DOWNLOAD',
  target_table VARCHAR(50) NOT NULL COMMENT '被操作表',
  target_id   VARCHAR(32)  NOT NULL COMMENT '被操作记录ID',
  detail      JSON                  COMMENT '变更前后摘要',
  operated_at DATETIME     NOT NULL DEFAULT CURRENT_TIMESTAMP,
  ip          VARCHAR(45),
  PRIMARY KEY (log_id),
  KEY idx_book_time (book_id, operated_at),        -- 按古籍查留痕
  KEY idx_user_time (user_id, operated_at)         -- 按操作人查留痕
);
```

### 2.3 为什么古籍影像文件不直接存入数据库

1. **体积与类型不适配**：古籍扫描是数百 MB 级 TIFF 大图，数据库按"行页"存储二进制会迅速膨胀表空间，写入/更新拖垮缓冲池，连累同表元数据查询性能；
2. **备份与恢复代价**：库内大对象使备份文件剧增、恢复时间不可控；而影像文件天然只增不改，放对象存储可独立做增量备份与生命周期管理；
3. **读取路径低效**：影像需经应用层直接流式分发/生成缩略图，走数据库等于所有大流量 IO 都要穿过数据库连接与 SQL 层，成为吞吐瓶颈；对象存储天然支持 HTTP 直链、CDN 分发与断点续传；
4. **耦合与扩展性**：文件本体入库会把存储方案与数据库绑死，违反"可更换数据库"的约束；以 `file_ref` 引用对象存储（如 MinIO/S3/OSS），换数据库、换存储互不影响；
5. **结论**：库中只存影像的**引用与描述性元数据**（路径、页码、格式、分辨率），本体放对象存储——既满足"影像/OCR 文本/元数据分开存储"的业务约束，也是行业标准做法。
